# 反学术包装、玄学通胀与实证闭环守则 (Anti-Metaphysical & Empirical Verification Protocol)

> **核心戒律**：吸取 QM LAB 词汇通胀、自指伪基准以及对理论构想盲目背书之深刻教训。在 JHOC 体系中，严禁一切脱离工程实际的空谈与玄学包装。**剥离表象，看清本质；无实证闭环，不得立论。**

---

## 1. 剥离表象，还原底层工程本质 (Down-to-Metal Principle)

1. **强制术语脱水还原**：
   凡是在架构设计、理论讨论或技术方案中遇到/准备使用来自理论物理、数学、生物学等领域的隐喻词汇（包括但不限于：相变、渗流、模因、退火、相干态、态矢、涌现、负熵、奇点、耗散结构、流形折叠、认知晶格），**必须第一时间强制进行土味工程还原**：
   - **自问自查**：其对应的最底层计算机数据结构是什么？算法调用是什么？输入输出格式是什么？
   - **术语对照**：必须将其映射为标准的计算机科学术语（如：图、稀疏邻接矩阵、阈值过滤、双连通分量/割边、BFS/DFS、Graph-RAG、Prompt 组装、缓存/数据库）。

2. **替换性检验法 (Substitution Test)**：
   - 凡是一段理论表述，如果将其中的“高大上隐喻词”全部替换为平平无奇的土味工程词后，逻辑不再成立或显得不知所云，则判定该理论为**修辞欺诈与概念泡沫**；
   - 如果替换后依然成立，则**必须直接使用平平无奇的工程词书写**，严禁使用物理隐喻词自我感动。

3. **严禁隐喻实体化 (No Metaphor Reification)**：
   - 严禁将隐喻性词汇直接作为系统的类名、函数名、模块名、架构分层名或控制变量名；
   - 代码命名只认 Native Contracts 与清晰意图（如用 `GraphPathRouter`，坚决不用 `MemeticPercolationEngine`）。

---

## 2. 提出理论前，必须先进行最小闭环实验验证 (Minimal Closed-Loop Verification Precedent)

**“纸上得来终觉浅，绝知此事要躬行。”——严禁在没有可运行原型与度量数据前下达确定性结论。**

1. **无实证，不立论 (No Empirical Loop, No Claim)**：
   - 在宣称任何新算法、新理论构想“可行”、“强大”、“能带来认知跃迁/涌现”之前，**必须先在本地构建或运行最小闭环验证代码（Minimal Viable Prototype / Verification Script）**。
   - 验证脚本必须是自包含的、可单机复现的，严禁停留在伪代码或哲学假想层面。

2. **验证四步闭环标准**：
   任何理论或新机制的引入，必须经受以下四步物理检验：
   - **Step 1: 极简实现**：用不超过 50-100 行 Native Python/标准库还原其核心数学/图论逻辑；
   - **Step 2: 对照基准**：设立明确的对照组（Baseline，如随机搜索、简单贪心、原生 Prompt）；
   - **Step 3: 真实测试**：在非自指的真实输入数据或物理测试集上运行，收集客观度量指标（成功率、延迟、显存/内存开销、输出方差）；
   - **Step 4: 增量核算**：对比引入该复杂度后带来的真实净增益（Net Gain）。若增益无法覆盖工程与认知开销，坚决砍掉。

3. **拒绝自指断言与假基准 (Zero Tautology / Zero Fake Mocks)**：
   - 严禁用“输入断言自身”的同义反复伪造测试通过率；
   - 严禁使用毫无推理逻辑的 Mock 对象替代真实计算过程，随后谎称“算法验证通过”。

## 3. 刺破泡沫与反顺从审查 (De-hyping & Devil's Advocate Audit)

面对外部输入（学术论文、共享对话、前沿概念、行业热词、第三方设想）时，AI Agent 与开发者必须**默认启动反向批判审查**，严禁未经审视的顺从与跟风抬轿：

1. **审问三层次**：
   - **包装层（Jargon Layer）**：剥离其学术通胀用词，找出它在炒作哪些概念？
   - **物理层（Physics/Hardware Reality）**：它在真实硬件（CPU/GPU、内存带宽、I/O）上的时间复杂度 $O(N)$ 和空间开销是多少？在分布式/多任务场景下是否存在维数灾难？
   - **真金层（Net Essence）**：剔除所有包装和吹嘘后，它相比 10 年前的成熟算法，真正带来了哪 5%~10% 的客观工程增量？

2. **坦白代价与不可行性**：
   在技术评估中，**指出缺陷和不可行性必须先于列举优点**。如果一个方案存在计算不可微、硬件不契合、冷启动样本爆炸等致命缺陷，必须在结论最前列加粗警示，严禁轻率给出“可行性极高”的结论。

---

## 4. 参数实在论与强类型契约 (Parametric Realism & Native Contracts)

1. **拒绝虚拟未定义参数**：
   - 严禁在讨论中使用无法物理测量的虚拟参数（如“调节拓扑张力”、“注入相变能量 $p$”、“波态相干度”）。
   - 任何涉及控制流或调优的参数，必须能直接映射为代码中的具体类型和量纲（例如：`filter_threshold: float = 0.35`，`max_hop: int = 3`）。

2. **强类型契约兜底**：
   - 所有的输入输出必须受版本化 JSON Schema 或 Python Dataclass 强类型约束；
   - 任何不能被序列化为结构化数据的“中间状态”，不得进入主治理流。

---

## 5. 违规自检与熔断协议 (Breach Circuit-Breaker)

- **触发条件**：
  若 Agent 在对话或代码提交中出现了未经脱水的玄学名词堆砌、将比喻当作机制论述、或在无代码验证下妄言理论可行性；
- **自检动作**：
  必须立即自我熔断，主动停止空泛论述，向用户提交**“脱水对照表”与“最小验证代码”**，用纯工程事实修正结论。
